# 第二课：业务知识的完整生命周期

> 第一课回答“LLM Wiki 是什么”。第二课继续回答一个更实际的问题：一条业务知识怎样从原始文档进入 Wiki，最后被大模型用于回答问题，并在出错后得到修复？

## 本课目标

学完这一课，你应该能够理解：

- 为什么原始文档不能直接等同于知识；
- 一条知识进入 Wiki 前要经过哪些加工；
- 业务层、语义层、元数据层和规则层如何协作；
- RAG 在运行时怎样检索这些知识；
- 如何记录从问题到答案的完整证据链；
- Badcase 如何反向推动知识库改进。

---

## 一、先看全局：一条知识经历了什么

一条业务知识的生命周期可以分成三个阶段。

### 阶段 A：知识生产

```text
原始材料
→ 来源登记
→ 事实抽取
→ 分类与建模
→ 冲突和边界处理
→ 生成 Wiki 页面
→ 质量检查
```

这一阶段负责把散落在文档中的信息，转化成结构清晰、来源可靠的知识。

### 阶段 B：知识消费

```text
用户问题
→ 问题理解
→ 检索知识
→ 选择指标和数据资产
→ 调用工具或生成 SQL
→ 得到结果
→ 生成答案
```

这一阶段负责让大模型和 Agent 使用知识完成真实任务。

### 阶段 C：知识改进

```text
记录回答过程
→ 评测结果
→ 发现 Badcase
→ 根因归类
→ 修复 Wiki / Skill / 检索
→ 回归验证
```

这一阶段负责让知识库随着使用不断变好。

把三个阶段连接起来，就是完整闭环：

```text
证据 → 知识 → 消费 → 评测 → 修复 → 新的知识版本
```

## 二、用“活跃商家数”贯穿整堂课

假设某份业务文档中写着：

> 近 30 天内至少产生一次有效经营行为的商家，定义为活跃商家。活跃商家数按商家 ID 去重统计。当前正式经营分析统一使用模型 `merchant_operation` 中的指标 `active_merchant_cnt`。

这段话看起来不长，但里面至少包含五类知识：

| 文本内容 | 知识类型 |
| --- | --- |
| 商家 | 业务实体 |
| 有效经营行为 | 业务概念和判断规则 |
| 近 30 天 | 时间窗口和修饰条件 |
| 按商家 ID 去重 | 指标粒度与计算规则 |
| `active_merchant_cnt` | 语义指标和数据资产映射 |

如果把整段话只作为一个普通文本块存进去，大模型可能读懂，也可能忽略其中某个关键条件。

知识建模的任务，是把这些信息拆开、分类，再建立明确关系。

---

## 三、步骤一：收集原始证据

### 1. 什么可以成为原始证据

常见来源包括：

- 业务白皮书；
- 产品 OnePager；
- 指标口径文档；
- Hive 表使用手册；
- Dataset 元数据；
- 生产 SQL；
- 会议纪要；
- 分析报告；
- 审批通过的业务规则。

### 2. 原始证据层应该做什么

原始证据层的主要职责是保真，而不是改写。

通常需要保留：

- 原始内容；
- 来源链接或文件位置；
- 文档标题；
- 作者或 Owner；
- 创建和更新时间；
- 业务范围；
- 文档状态；
- 抓取时间和版本。

### 3. 为什么不应该随意修改原始证据

如果原始材料被直接改写，后续就很难判断：

- 内容原来就是这样写的；
- 还是知识抽取过程中被修改了；
- 某项结论是业务方确认的；
- 还是模型自己补充的。

所以常见原则是：

> 原始证据只负责保存事实输入，Wiki 负责生产可复用知识。

---

## 四、步骤二：登记来源与状态

文档被收集以后，不能立刻把所有内容升级成稳定规则。

首先要判断来源的性质。

| 来源状态 | 含义 | 是否可以直接作为稳定规则 |
| --- | --- | --- |
| Production | 已正式生效 | 通常可以，但仍需保留来源 |
| Approved | 已审批、等待或正在发布 | 需标明生效时间 |
| WIP | 正在编写 | 不应直接升级 |
| Experiment | 实验方案或实验结果 | 只能在对应实验边界内使用 |
| Strategy Draft | 策略草案 | 不能作为正式口径 |
| Deprecated | 已废弃 | 仅用于历史追溯 |

还要记录适用范围：

- 哪个国家或 Region；
- 哪条业务线；
- 哪个产品版本；
- 哪段时间有效；
- 对哪些用户或商家类型生效。

例如，“近 30 天活跃商家”可能只适用于经营分析，而风控团队可能使用另一套活跃定义。没有范围标记，两个定义都会看起来像正确答案。

---

## 五、步骤三：从文档中抽取 Claim

### 1. 什么是 Claim

Claim 可以理解为一条可以被验证的明确陈述。

例如：

- 商家的唯一标识是 `merchant_id`。
- 活跃商家数按 `merchant_id` 去重。
- 活跃窗口为最近 30 天。
- 指标 `active_merchant_cnt` 属于模型 `merchant_operation`。

这些都是独立 Claim。

“这份文档介绍了商家经营情况”不是一个高质量 Claim，因为它过于模糊，无法明确验证。

### 2. 为什么要拆 Claim

拆分以后，系统可以：

- 为每条事实绑定来源；
- 单独判断可信度；
- 发现不同文档之间的冲突；
- 把事实分配给正确的 Wiki 页面；
- 在回答时只检索真正需要的部分。

### 3. 一条高质量 Claim 应包含什么

| 字段 | 作用 |
| --- | --- |
| 主体 | 这条事实描述谁 |
| 谓词 | 主体和对象是什么关系 |
| 对象或值 | 具体结论是什么 |
| 条件 | 在什么情况下成立 |
| 时间 | 什么时候生效 |
| 来源 | 依据来自哪里 |
| 状态 | 已确认、待确认还是已废弃 |

例如：

```yaml
subject: 活跃商家数
predicate: 去重粒度
object: merchant_id
condition: GEC 商家经营分析
effective_time: 2026-07-01
source: 商家经营指标口径文档
status: production
```

不一定真的使用 YAML 保存，但知识设计时应具备这些信息。

## 六、步骤四：给知识正确分类

抽取 Claim 后，需要判断它应该进入哪一层。

### 业务知识

描述现实业务世界：

- 商家是什么；
- 店铺是什么；
- 商家经营包含哪些过程；
- 商家和店铺是什么关系。

### 语义知识

描述业务语言如何转化成可计算定义：

- 活跃商家数的定义；
- GMV 的统计口径；
- 国家、行业等维度的含义；
- 时间窗口和修饰词。

### 元数据知识

描述数据资产本身：

- 模型和 Dataset；
- Hive 表与字段；
- 主键和分区；
- Owner、TTL、血缘。

### 规则知识

描述使用知识和数据时必须遵守的约束：

- 选表优先级；
- 商家与店铺如何 JOIN；
- 日期如何映射到分区；
- 哪些字段不能混用；
- 如何避免重复计算。

### FAQ 和洞察

描述常见问题及可复用分析经验：

- 为什么两个系统中的 GMV 不一致；
- 活跃商家数异常下降应该如何拆解；
- 某类问题应优先检查哪些维度。

分类错误会影响检索和维护。例如，把 Hive 表当作业务实体，会导致模型把物理存储结构误认为现实业务对象。

---

## 七、步骤五：建立语义契约

语义契约回答的是：一个业务说法怎样被稳定地解释和计算。

以“活跃商家数”为例，至少需要明确：

| 项目 | 示例 |
| --- | --- |
| 业务名称 | 活跃商家数 |
| 定义 | 近 30 天至少发生一次有效经营行为的商家数 |
| 统计对象 | 商家 |
| 去重主键 | `merchant_id` |
| 时间窗口 | 滚动 30 天 |
| 计算方式 | `COUNT(DISTINCT merchant_id)` |
| 必要条件 | 经营行为必须有效 |
| 默认时区 | 业务约定时区 |
| 适用范围 | GEC 商家经营分析 |
| 不适用范围 | 风控活跃判断 |
| 指标资产 | `active_merchant_cnt` |

语义契约的重要性在于：业务方、数据开发、分析师和大模型使用的是同一个定义。

如果定义只存在于人的脑中或某段 SQL 里，模型很难稳定复用。

---

## 八、步骤六：连接语义和数据资产

业务定义还不能直接执行，需要继续连接到物理数据。

```text
活跃商家数
→ 语义指标 active_merchant_cnt
→ 语义模型 merchant_operation
→ Aeolus Dataset
→ Hive 表
→ merchant_id、event_type、ds 等字段
```

连接过程中需要回答：

- 指标属于哪个模型；
- Dataset 是否已经包含正式指标；
- Dataset 的字段角色是指标还是维度；
- 底层依赖哪些 Hive 表；
- 表的粒度和主键是什么；
- 日期分区是什么；
- 字段是否存在枚举和空值风险。

这一步的核心不是“多加几个链接”，而是建立可执行证据链。

当模型需要生成 SQL 时，应该能够沿着这条链从业务语言下钻到数据字段。

---

## 九、步骤七：生成 Wiki 页面

知识进入 Wiki 后，每种页面应承担不同职责。

### 一个好的指标页面通常包含

- 指标名称和别名；
- 业务定义；
- 统计对象和粒度；
- 计算方法；
- 时间窗口；
- 必要过滤条件；
- 适用与不适用范围；
- 所属模型；
- 来源与更新时间；
- 常见误用提醒。

### 一个好的 Hive 表页面通常包含

- 表名和用途；
- 表粒度；
- 主键；
- 分区字段；
- 核心字段；
- 上下游血缘；
- Owner；
- 查询风险；
- 来源。

### 为什么不能只生成大而全的页面

页面过大时：

- 检索很难精确命中；
- 无关内容会占用模型上下文；
- 单条事实很难维护；
- 修改一处容易影响其他内容；
- 来源粒度不清晰。

但页面也不能拆得过碎，否则知识关系会断裂、检索结果会失去上下文。

合理原则是：

> 一个页面围绕一个稳定、可独立复用的知识对象组织，同时保留必要上下文和关联入口。

## 十、步骤八：运行知识质量门禁

知识写入 Wiki 后，至少需要检查两类质量。

### 1. 结构质量

- 页面是否符合模板；
- 内部链接是否有效；
- 页面能否从入口到达；
- 来源是否存在；
- 必要章节是否完整；
- 文件名和对象名称是否重复；
- 每类页面是否由正确的流程负责。

### 2. 内容质量

- Claim 是否忠于原始证据；
- 指标定义是否完整；
- 状态和生效范围是否明确；
- 多个来源是否发生冲突；
- 语义到数据资产的连接是否正确；
- 是否把实验结论误写成正式规则。

结构检查通过只能说明“页面格式合格”，不能证明模型一定能答对真实问题。

---

## 十一、步骤九：为检索建立索引

Wiki 页面需要被检索系统处理，才能在运行时交给大模型。

### 1. Chunking

Chunking 是把页面切成适合检索的片段。

切得过大：

- 容易带入大量无关内容；
- Token 成本较高；
- 关键事实可能被埋在中间。

切得过小：

- 事实失去上下文；
- 指标名称和适用范围可能分离；
- 模型无法理解片段之间的关系。

更合理的方式通常是按页面章节和知识对象切分，同时保留：

- 页面标题；
- 对象类型；
- 来源；
- 适用范围；
- 父级页面；
- 相关对象链接。

### 2. Embedding

Embedding 把文本转换为向量，使系统可以按照语义相似度检索。

例如用户问“最近有经营行为的商家数量”，即使页面标题是“活跃商家数”，语义检索仍可能命中。

### 3. 混合检索

企业知识通常适合同时使用：

- 关键词检索：适合表名、字段名、指标 ID；
- 向量检索：适合自然语言和同义表达；
- 元数据过滤：适合 Region、业务域、状态和时间；
- 关系下钻：适合指标到模型、Dataset 和 Hive 表的连接。

仅靠单一向量相似度，很难稳定完成复杂业务检索。

---

## 十二、步骤十：运行时回答用户问题

当用户问“过去 30 天活跃商家有多少”时，一个较完整的运行流程如下。

### 1. 问题理解

识别：

- 业务对象：商家；
- 指标：活跃商家数；
- 时间：过去 30 天；
- 动作：查询数据；
- 可能缺失的信息：Region、业务范围、截止日期。

### 2. 语义检索

检索：

- 活跃商家数指标；
- 商家实体；
- 时间窗口规则；
- 指标适用范围。

### 3. 数据资产选择

按照满足度和使用规则选择：

- 已有标准指标的模型或 Dataset；
- 或需要直接查询的 Hive 表。

### 4. 执行前检查

- 日期是否解析为明确范围；
- 分区是否存在；
- 粒度是否一致；
- 去重主键是否正确；
- 是否需要 JOIN；
- 是否有权限。

### 5. 执行与回答

查询完成后，答案需要说明：

- 查询结果；
- 使用的指标口径；
- 时间范围和时区；
- 主要数据来源；
- 可能影响解释的限制。

---

## 十三、Answer Trace：记录答案是怎样产生的

为了能够评测和排错，系统应记录完整的 Answer Trace。

```text
原始问题
→ 解析后的业务意图
→ 召回的知识页面
→ 选中的指标和维度
→ 使用的规则
→ 选中的模型、Dataset 或 Hive 表
→ 生成的 QueryPlan / SQL
→ 工具执行结果
→ 最终答案
```

Trace 至少应帮助回答：

- 模型看到了哪些知识？
- 为什么选择这个指标？
- 为什么选择这张表？
- 哪条规则影响了 SQL？
- 查询是否真正执行成功？
- 最终结论来自数据，还是模型推测？

没有 Trace，模型答错后通常只能看到最终答案，很难找到真正原因。

---

## 十四、步骤十一：评测答案

一条回答可以从三个层面评测。

### 1. 检索层

- 是否召回正确指标；
- 是否召回关键业务规则；
- 是否引入不适用或过期知识；
- 正确知识在结果中排名是否足够靠前。

### 2. 推理和 SQL 层

- 是否选择正确粒度；
- 时间窗口是否正确；
- 去重方式是否正确；
- 选表和字段是否正确；
- SQL 是否可以执行；
- JOIN 是否造成数据膨胀。

### 3. 最终答案层

- 是否直接回答问题；
- 是否与查询结果一致；
- 是否说明关键口径；
- 是否引用可靠证据；
- 信息不足时是否诚实说明。

---

## 十五、步骤十二：从 Badcase 反向修复

假设模型将“活跃商家数”错误地按 `shop_id` 去重。

不要马上在 Prompt 里追加一句“必须使用 merchant_id”。先根据 Trace 判断根因。

### 情况 A：知识库没有去重粒度

修复指标语义页面，并补充来源。

### 情况 B：知识存在，但检索没有召回

修复标题、别名、Chunk、Embedding 或检索规则。

### 情况 C：知识已召回，但模型忽略

修复 Skill、上下文排序或确定性校验规则。

### 情况 D：SQL 生成正确，执行层改写错误

修复 SQL 工具或执行协议。

### 情况 E：只有某个 Region 使用不同口径

补充适用范围和冲突裁决规则，而不是粗暴删除其中一个定义。

Badcase 归因的基本原则是：

> 修复真正发生错误的层，不要把所有问题都堆进 Prompt。

---

## 十六、步骤十三：回归验证

修复后至少重新运行两类测试。

### 目标用例

确认刚才的错误已经修好，例如：

- “活跃商家数按什么粒度统计？”
- “过去 30 天活跃商家有多少？”

### 相邻用例

确认修改没有破坏其他概念，例如：

- 活跃店铺数是否仍按 `shop_id` 去重；
- 风控活跃商家的特殊定义是否仍然有效；
- 其他 Region 的指标是否没有被错误覆盖。

这就是回归测试的意义：不仅证明“新问题修好了”，还要证明“旧能力没有被修坏”。

---

## 十七、完整生命周期中的关键产物

| 阶段 | 主要产物 |
| --- | --- |
| 原始证据 | 文档、元数据快照、生产 SQL、版本信息 |
| 来源登记 | 来源页、状态、Owner、适用范围 |
| 事实抽取 | Claim 列表、来源定位、置信状态 |
| 知识建模 | 业务、语义、元数据、规则页面 |
| 资产连接 | 指标—模型—Dataset—Hive—字段关系 |
| 质量门禁 | 链接、结构、来源和冲突报告 |
| 检索索引 | Chunk、Embedding、关键词及过滤字段 |
| 运行消费 | QueryPlan、SQL、执行结果、答案 |
| 可观测性 | Answer Trace、日志、引用证据 |
| 评测改进 | 黄金问题、评分、Badcase、修复记录、回归结果 |

## 十八、新手检查清单

当你准备把一份文档加入 LLM Wiki 时，可以依次检查：

### 来源检查

- [ ] 来源是否可信？
- [ ] 是否记录作者、Owner 和更新时间？
- [ ] 文档是正式规则、WIP、实验还是历史材料？
- [ ] 是否明确 Region、业务和时间范围？

### 知识检查

- [ ] 是否抽取成可验证的 Claim？
- [ ] 每条 Claim 是否有来源？
- [ ] 是否区分业务、语义、元数据和规则？
- [ ] 是否发现重复或冲突定义？
- [ ] 是否明确不适用范围？

### 消费检查

- [ ] 用户可能用哪些自然语言表达这条知识？
- [ ] 关键词和同义词能否被检索？
- [ ] 指标能否连接到模型、Dataset 或表？
- [ ] 是否包含生成 SQL 所需的粒度和字段信息？

### 评测检查

- [ ] 是否有问题能够验证这条知识？
- [ ] 正确答案和证据是什么？
- [ ] 修改后是否运行目标用例和相邻用例？
- [ ] Badcase 是否留下归因与修复记录？

## 十九、本课最重要的三个结论

### 结论一：知识生产不是复制文档

真正的知识生产包括来源登记、Claim 抽取、分类、边界判断、冲突处理和关系建立。

### 结论二：知识只有被正确消费才产生价值

页面数量和结构检查只是基础。知识还必须能够被检索、组合，并帮助模型完成正确的业务决策和数据查询。

### 结论三：Badcase 是知识库成长的主要输入

新文档告诉我们“又有什么资料”，Badcase 告诉我们“系统真正缺什么”。成熟知识库会同时吸收两种输入，但后者更能直接推动效果提升。

## 课后练习

任选一项你熟悉的业务指标，尝试填写下面的模板：

```markdown
# 指标名称

## 业务定义

## 统计对象

## 统计粒度与去重主键

## 时间窗口与时区

## 计算方式

## 必要过滤条件

## 适用范围

## 不适用范围

## 所属模型或 Dataset

## 底层表和字段

## 常见误用

## 来源与更新时间
```

完成后，再设计三个问题：

1. 一个验证指标定义的问题；
2. 一个验证数据资产选择的问题；
3. 一个验证完整 SQL 或查询结果的问题。

如果这三个问题都能被稳定回答，这条知识才算开始具备可消费、可评测的形态。
