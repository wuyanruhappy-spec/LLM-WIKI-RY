# LLM Wiki 入门与建设思考

> 面向第一次接触 LLM 知识库的读者。目标是用尽量简单的语言，讲清楚 LLM Wiki 是什么、为什么需要它、内部有哪些组成部分，以及怎样把一个静态知识库逐步建设成可持续改进的业务知识系统。

## 先记住一句话

> LLM Wiki 是一套让大模型能够找到正确业务知识、理解业务口径、引用可信证据，并据此完成任务的知识系统。

普通 Wiki 主要服务人；LLM Wiki 同时服务四类消费者：

- 人：阅读资料、查询定义、寻找数据资产。
- 大模型：检索知识、理解业务、生成回答。
- Agent：按照规则完成查数、SQL 生成、分析和归因。
- 评测系统：检查模型是否答对，判断错误发生在哪个环节。

---

## 一、为什么大模型还需要知识库

可以把大模型想象成一个很聪明的新员工。

它具备通用语言、推理、写作和编程能力，但通常不了解一家公司的内部事实：

- “商家”和“店铺”有什么区别？
- GMV 使用支付口径还是下单口径？
- 指标是否需要扣除退款？
- 某个指标应当查询哪个 Dataset？
- 哪张 Hive 表才是正式生产表？
- 日期字段使用 `date`、`p_date` 还是 `ds`？
- 某项策略已经正式生效，还是仍处于实验阶段？

没有知识库时，大模型只能根据通用经验进行推测。企业场景最危险的情况不是模型明确表示“不知道”，而是它给出一个看起来专业、实际口径错误的答案。

因此，企业知识库的核心价值不是简单增加文字，而是：

1. 给模型提供企业内部事实。
2. 明确事实的适用范围和来源。
3. 告诉模型应该怎样使用这些事实。
4. 减少模型依靠猜测完成任务的空间。

## 二、知识、文档和知识库的区别

### 1. 文档是知识的来源

白皮书、OnePager、会议纪要、Hive 表手册、指标说明和数据集文档都属于原始材料。

一篇文档中可能同时包含：

- 稳定的业务事实；
- 指标和字段定义；
- 临时策略；
- 实验结果；
- 尚未上线的规划；
- 已经过期的操作方式。

因此，不能简单地把所有文档放进向量数据库，就认为知识库已经建成。

### 2. 知识是经过治理的事实

文档进入知识库前，通常需要经过：

```text
原始文档
→ 识别事实
→ 分类
→ 去重与冲突处理
→ 标记适用范围
→ 关联来源
→ 连接其他知识
```

只有经过这些步骤，文档中的内容才能变成模型可以稳定消费的知识。

### 3. 知识库是知识的组织和运行系统

一个好的知识库不仅存储内容，还要回答：

- 哪些知识值得长期保留？
- 哪个来源更权威？
- 多份文档冲突时相信谁？
- 某条规则适用于哪个地区、业务和时间范围？
- 一个业务概念如何连接到指标、模型、Dataset 和 Hive 表？
- 模型答错以后应该修改哪一层？

## 三、LLM Wiki 的八个核心层次

可以把 LLM Wiki 理解成八层结构。

| 层次 | 通俗解释 | 常见内容 |
| --- | --- | --- |
| 原始证据层 | 未加工的原始材料 | 白皮书、OnePager、Hive 手册、数据集说明 |
| 来源层 | 对原始材料的整理和引用入口 | 来源摘要、文档状态、适用范围 |
| 业务层 | 公司业务是如何运转的 | 业务域、商家、店铺、商品、经营过程 |
| 语义层 | 业务指标和维度是什么意思 | GMV、活跃商家数、国家、行业 |
| 元数据层 | 数据具体存在哪里 | 模型、Dataset、Hive 表、字段、分区、血缘 |
| 规则层 | 使用知识时必须遵守什么 | 选表、粒度、JOIN、日期、口径规则 |
| FAQ/洞察层 | 常见问题和分析经验 | GMV 对不上、指标波动诊断方法 |
| Skill 层 | Agent 应当怎样执行任务 | 选指标、选表、生成 SQL、执行、解释结果 |

一个典型仓库可能采用如下结构：

```text
raw/
└── 原始文档和元数据证据

wiki/
├── sources/       来源
├── business/      业务知识
├── semantics/     指标与维度语义
├── metadata/      模型、Hive 表和 Dataset
├── rules/         使用规则
├── faq/           常见问题
└── insights/      分析方法

skills/
└── 告诉 Agent 如何使用这些知识
```

这种分层的意义是让每一类知识承担清晰职责。例如，Hive 表不是业务实体，字段也不是业务概念；它们属于元数据。业务实体描述现实世界中的稳定对象，例如商家、店铺和商品。

## 四、用一个真实问题理解完整链路

假设用户问：

> 昨天跨境商家的 GMV 为什么下降？

一个可靠的 AI 不应该立刻开始写 SQL，而应当依次完成以下工作。

### 第一步：理解业务问题

- “跨境商家”如何定义？
- 查询粒度是商家还是店铺？
- 包含哪些市场？
- “下降”指环比、同比，还是相对某个业务基准下降？

这一阶段主要消费业务知识。

### 第二步：确定语义口径

- GMV 是支付 GMV 还是下单 GMV？
- 是否扣除退款？
- 使用哪个币种？
- “昨天”按照哪个时区计算？

这一阶段主要消费指标语义和业务规则。

### 第三步：找到数据资产

- 哪个语义模型包含这个指标？
- 是否有可以直接查询的 Aeolus Dataset？
- 如果没有，应该使用哪张 Hive 表？

这一阶段主要消费模型、Dataset 和 Hive 元数据。

### 第四步：确定 SQL 规则

- 日期分区字段是什么？
- 商家和店铺如何关联？
- JOIN 是否会形成一对多关系？
- 是否会造成 GMV 重复计算？
- 哪些分区已有数据？

这一阶段主要消费查询规则、表结构和数据血缘。

### 第五步：执行和解释

- 生成并执行 SQL；
- 按国家、行业或商家层级拆解结果；
- 判断下降来自商家数量、活跃率，还是单商家产出；
- 给出结论、口径说明和证据。

完整链路可以表示为：

```text
业务问题
→ 业务对象和过程
→ 指标与口径
→ 维度与限定条件
→ 语义模型
→ Dataset / Hive 表
→ 字段、分区与 JOIN
→ SQL
→ 查询结果与解释
```

一个可靠答案通常不是从某一篇文档直接复制出来的，而是把多个层次的知识连接后得到的。

## 五、什么是语义层

语义层负责把业务语言翻译成数据语言。

用户说：

> 活跃商家有多少？

数据系统真正需要知道的是：

- “商家”的唯一 ID 是什么；
- “活跃”的判断条件是什么；
- 统计粒度是日、周还是月；
- 使用什么去重方式；
- 对应哪个模型和指标；
- 底层使用哪个字段或表达式；
- 必须附加哪些过滤条件。

可以把语义层理解成一套业务语言与数据语言之间的翻译契约：

| 业务语言 | 数据语言 |
| --- | --- |
| 活跃商家数 | 指标定义、计算表达式和去重方式 |
| 国家 | `country_code` 等标准维度字段 |
| 昨天 | 明确日期、时区和数据分区 |
| 跨境商家 | 商家类型及适用范围筛选条件 |

没有语义层，大模型仍然可能写出技术上可以运行、业务上却错误的 SQL。

## 六、LLM Wiki、RAG 和向量数据库的关系

### 1. RAG 是寻找信息的方法

RAG 的基本流程是：

```text
用户提问
→ 检索相关内容
→ 将内容放入模型上下文
→ 模型根据内容生成答案
```

它主要解决“去哪里找相关资料”。

### 2. Wiki 是被治理的知识资产

Wiki 负责决定：

- 什么内容可以作为稳定知识；
- 知识应当如何分类；
- 哪个来源更权威；
- 指标、模型、Dataset 和表之间有什么关系；
- 哪些规则必须执行；
- 出现冲突时如何裁决。

它主要解决“找到的东西是否可信，以及应当怎样使用”。

### 3. 向量数据库只是检索基础设施之一

向量数据库通过 Embedding 表示文本语义，帮助系统找到意思相近的内容。它很有用，但不能自动解决：

- 知识冲突；
- 指标口径；
- 数据粒度；
- 版本和生效时间；
- 证据优先级；
- 复杂关系推理。

所以三者的关系可以概括为：

> Wiki 管理知识，RAG 负责检索知识，向量数据库是实现语义检索的一种工具。

只有 RAG、没有治理好的 Wiki，系统可能非常准确地检索到一份已经过期的文档。

## 七、什么叫知识可追溯

每一项重要结论都应当能回答：

> 你凭什么这么说？

例如：

```text
“活跃商家数使用指标 X”
→ 指标语义页面

“指标 X 属于模型 Y”
→ 语义模型页面

“模型 Y 使用 Dataset Z”
→ Dataset 元数据页面

“Dataset Z 来自 Hive 表 T”
→ 数据血缘或表元数据页面

“Hive 表 T 按 ds 分区”
→ Hive 表使用手册
```

这条从结论回到来源的路径叫作证据链。

可追溯性很重要，因为模型答错时，需要进一步区分：

- 原始材料本身有误；
- 知识抽取错误；
- 多个来源发生冲突；
- 检索没有找到正确知识；
- 模型理解或推理错误；
- SQL 转换错误；
- 数据执行或数据质量有问题。

## 八、知识库不是建完就结束

一个真正有效的知识库需要形成持续循环：

```text
收集证据
→ 抽取和组织知识
→ 建立知识关联
→ 模型或 Agent 消费
→ 使用真实问题评测
→ 发现 Badcase
→ 判断错误原因
→ 修复 Wiki 或 Skill
→ 回归验证
```

例如，模型答错“活跃商家数”，可能对应完全不同的修复方式：

| 现象 | 可能原因 | 应当修复的位置 |
| --- | --- | --- |
| 没有找到指标 | 检索召回不足 | 索引、别名或同义词 |
| 同时找到两个冲突指标 | 适用边界不清 | 指标语义和裁决规则 |
| 指标正确但选表错误 | 资产关系缺失 | 模型、Dataset、Hive 映射 |
| SQL 出现重复计算 | JOIN 粒度错误 | 查询规则或 Skill |
| SQL 正确但结论错误 | 分析能力不足 | Insight 或分析 Skill |
| 使用了过时策略 | 状态和时间边界不清 | 来源状态、生效时间 |

因此，页面数量增加不等于知识库质量提升。真正的提升应表现为：

- 真实问题正确率提高；
- 模型猜测减少；
- SQL 口径错误减少；
- Badcase 可以快速定位；
- 知识修改后不会破坏原本正确的能力。

## 九、怎样判断一个知识库好不好

### 1. 找得到

用户用自然语言提问时，系统可以召回正确的业务知识、指标和数据资产。

### 2. 看得懂

页面不只是堆放字段，还包含业务含义、适用范围、状态和使用方法。

### 3. 连得起来

业务概念、指标、维度、模型、Dataset 和 Hive 表能够形成完整证据链。

### 4. 不容易误用

粒度、时区、分区、JOIN、实验状态和地区范围等风险都有明确说明。

### 5. 能证明有效

系统有真实问题集、Badcase 归因和回归评测，而不仅仅检查页面数量和失效链接。

## 十、从“建库”转向“知识闭环”

当仓库已经能够稳定生成大量页面、保证链接可达并通过结构质量门禁后，下一阶段不应继续单纯追求页面数量。

更重要的问题是：

- 用户提出真实问题时，能否召回正确知识？
- 指标、维度、模型、Dataset 和 Hive 表能否正确连接？
- 生成的 SQL 是否符合业务口径？
- 最终答案是否真正解决了用户的问题？
- 回答失败后能否快速定位并修复？

因此，知识库下一阶段的定位可以从“文档集合”升级为：

> 一套让 AI 能够基于证据理解业务、选择语义资产、生成正确查询，并通过评测持续修复的业务语义控制面。

这套系统至少应承担四类能力：

| 能力 | 需要解决的问题 |
| --- | --- |
| 业务理解 | 用户问的是哪个对象、过程、地区和业务阶段？ |
| 语义裁决 | 应该使用哪个指标、维度、限定条件和统计粒度？ |
| 数据落地 | 应该选择哪个模型、Dataset、Hive 表、字段和 JOIN？ |
| 错误修复 | 错误来自知识、检索、推理、SQL、执行还是解释？ |

## 十一、知识库评测的三个层次

### 1. 语义覆盖与召回

检查：

- 正确业务域是否被召回；
- 正确指标、维度和模型是否进入上下文；
- 是否遗漏关键口径和风险规则；
- 是否召回了已经过期或不适用的知识。

### 2. SQL 一致性

检查：

- 选表、字段、粒度和分区是否正确；
- 指标实现是否符合语义定义；
- JOIN 是否造成重复计算或粒度膨胀；
- 日期与时区是否被正确转换。

### 3. 端到端消费

检查：

- 最终答案是否回答用户的问题；
- 是否提供必要的口径说明和证据；
- 是否能正确解释查询结果；
- 信息不足时是否会明确说明，而不是编造答案。

结构门禁回答“页面是否合法”，业务评测回答“模型使用这些页面后是否真的答对”。两者都需要，但不能互相替代。

## 十二、最值得优先建设的三个能力

### 1. 黄金业务问题集

先选择 30～50 个高频、高价值、容易出错的真实问题，例如：

- 商家经营表现如何？
- 某类商家的 GMV 为什么下降？
- 商家活跃率应该使用哪个口径？
- 店铺粒度和商家粒度怎样转换？
- 一个问题应走 Nuwa 模型、Aeolus Dataset 还是 Hive 表？

每个问题不仅保存最终 SQL，还应保存标准的业务理解、语义选择和资产链路。

### 2. Answer Trace

每次回答都记录：

```text
问题理解
→ 命中的业务知识
→ 选中的指标和维度
→ 选中的模型、Dataset 或表
→ 使用的规则
→ 生成的 SQL
→ 查询结果
→ 最终答案
```

有了这条轨迹，Badcase 才能被准确归因。

### 3. 变更后的回归评测

每次新增或修改知识，不仅运行结构和链接检查，还要运行相关业务问题的回归集。

质量门禁需要逐步从：

> 页面是否合法？

升级为：

> 这次修改有没有让真实问题答得更好，并且没有破坏已有能力？

## 十三、新手最需要避免的误区

### 误区一：把所有文档放进向量库就完成了知识库

向量检索只能帮助找到相似内容，不能自动解决事实冲突、时效性、口径和权限问题。

### 误区二：页面越多，知识库越好

大量低价值、重复或孤立页面会制造检索噪声。知识的可用性比页面数量更重要。

### 误区三：模型找到相关内容就会答对

检索正确以后，模型仍然可能选错指标、误解粒度、错误 JOIN 或错误解释数据。

### 误区四：只有模型答错才算 Badcase

没有引用证据、使用过期知识、答案不可复现、SQL 无法稳定执行，同样属于质量问题。

### 误区五：知识库建成后只需要定期同步文档

真正的知识库运营应由真实问题、评测结果和 Badcase 驱动，而不是只由新文档驱动。

## 十四、核心术语速查

| 术语 | 简单解释 |
| --- | --- |
| LLM | 具备语言理解与生成能力的大模型 |
| Wiki | 经过组织、治理和关联的知识体系 |
| RAG | 先检索资料，再让模型基于资料回答 |
| Embedding | 把文本转换成可用于语义比较的向量 |
| Chunk | 为检索而切分的文档片段 |
| Semantic Layer | 将业务语言翻译为数据口径和资产的语义层 |
| Metadata | 表、字段、分区、Owner、血缘等数据资产信息 |
| Dataset | 面向分析消费组织的数据集合 |
| Skill | 指导 Agent 完成特定任务的流程和规则 |
| Agent | 能够规划步骤、调用工具并完成任务的 AI 系统 |
| Eval | 用测试问题和标准检查系统质量 |
| Badcase | 系统回答或执行失败的具体案例 |
| Regression | 修改系统后重新测试，确认旧能力没有退化 |
| Trace | 记录系统从问题到答案的完整决策和执行路径 |

## 十五、建议学习路线

### 阶段一：理解基础概念

重点掌握：

- 文档、知识和知识库的区别；
- Wiki、RAG 和向量数据库的关系；
- 业务层、语义层和元数据层的职责。

### 阶段二：学习知识建模

重点掌握：

- 如何从文档中抽取稳定事实；
- 如何定义实体、过程、指标和维度；
- 如何表达来源、状态、时间和适用范围；
- 如何建立指标到数据资产的证据链。

### 阶段三：学习检索与消费

重点掌握：

- Chunking、Embedding 和检索；
- Query Rewrite、混合检索和重排序；
- 如何控制上下文；
- Agent 如何根据 Skill 使用 Wiki。

### 阶段四：学习评测与归因

重点掌握：

- 黄金问题集；
- 检索评测与端到端评测；
- Answer Trace；
- Badcase 分类和根因定位；
- 回归测试。

### 阶段五：建立自进化闭环

最终形成：

```text
真实问题
→ 检索与生成
→ 白盒评测
→ Badcase 归因
→ 修复 Wiki / Skill
→ 回归验证
```

---

## 总结

初学者可以先记住三个判断：

1. 知识不等于文档。文档是来源，知识需要经过抽取、治理和关联。
2. 检索正确不等于回答正确。语义、口径、SQL 和解释都可能继续出错。
3. 建库不是终点。真实问题驱动的评测、归因、修复和回归闭环，才决定知识库是否真正有效。

用一句话概括整个体系：

> 原始材料提供证据，Wiki 组织知识，语义层翻译业务，Skill 指导执行，评测系统发现并推动修复问题。
